### Task 205: `/api/scan` fails about half the time, and fails silently

**Severity: Blocked launch** · Found 2026-09-13 running the first real end-to-end extraction against production, once the owner budget was unfrozen. **Root cause found and fixed 2026-09-14.** One item remains open; see the end.

#### What was observed

Four identical submissions of the same text through the real UI:

```
attempt 1   502 /api/scan   provider_invalid_response
attempt 2   200 /api/scan   then 502 /api/summarize
attempt 3   502 /api/scan   provider_invalid_response
attempt 4   502 /api/scan   provider_invalid_response
```

Same input, same model, different outcome. A failure also showed the user **nothing**: zero `error-notification` elements in the DOM, input cleared, no message.

#### The cause

One comparison inside the vendored Scanner:

```js
// vendor/event-every-scanner/dist/openrouter/wire-schema.js:117
if (ev.endOffset > source.text.length) throw new z.ZodError([...])
//  "Text evidence endOffset 40 exceeds source text length 39"
```

The model extracts the event **correctly**, then miscounts a character offset in its evidence citation by a few positions, and the Scanner discards the entire observation for it. Across 27 ground-truth inputs this single check was **9 of 11 failures - 82%**.

Nothing downstream ever wanted those offsets. `toDurableScanReplay` projects every claim through `projectClaim`, which sets `evidence: []`, and `DurableScanReplaySchema` requires `evidence.length === 0`. The app was destroying good extractions to satisfy a contract it deletes one function later and refuses to store.

Why it took so long to see: `response.js:88-94` wraps `observationFromWire` in a bare `catch {}` and rethrows `adapterError("invalid_observation")`, discarding the `ZodError`. The error string named no field. Nothing was diagnosable until that error was recovered by re-validating captured output directly against `WireProviderScanObservationSchema`.

#### The fix

`src/server/scanner/transport.ts` nulls both evidence offsets before the Scanner parses the completion. Both together - the wire schema permits `startOffset === null && endOffset === null` explicitly, and image evidence already requires it; nulling one fails the same refine. It lives in `src/` rather than `vendor/`, which is generated by `bun run vendor:scanner` and would lose the edit on the next re-vendor.

Measured on the same eval, same model, same n=54:

| | before | after |
| --- | --- | --- |
| SCHEMA (survived validation) | 70% (95% CI 57-81) | **98%** (90-100) |
| CORRECT (right event extracted) | 44% (95% CI 32-58) | **78%** (65-87) |

The correctness intervals do not overlap. Verified end to end against production: *"Team standup on Friday March 13 2026 at 9:30am in the Blue Room"* returns title `Team standup`, location `Blue Room`, `2026-03-13`, `09:30`.

#### What the first attempt got wrong, because it is the more useful lesson

The first investigation concluded the **model** was the problem, measured `deepseek-v4-flash` at 50% against `deepseek-v4.1-flash` at 100%, and recommended switching. All of that was wrong, and an independent review dismantled it:

- **Schema survival was being scored as success.** A run counted as passed when Zod did not throw - and an empty candidate list validates perfectly. It was measuring "is this well-formed JSON", not "did it find the event".
- **n=6 across 3 inputs is 3 data points**, nowhere near enough to separate 50% from 100%.
- **Three hand-picked sentences are anecdotes.** An extractor breaks on *shapes* - relative dates, implicit years, timezones, multiple events, text with no event at all - and none were represented.

Re-measured properly at n=54, the ordering **reversed**: current 44% correct, candidate 33%, intervals overlapping. The original result was sampling noise, and switching models would have changed nothing while the bug was declared closed.

The eval was rebuilt around that: `scripts/scan-eval-cases.ts` holds 27 hand-written ground-truth cases across 11 categories including negatives, and `scripts/measure-scan-reliability.ts` scores schema survival and extraction correctness **separately**, with Wilson intervals. `scripts/diagnose-scan-failure.ts` recovers the swallowed `ZodError`.

#### Still open

- [ ] **Negative inputs return a null-filled placeholder.** Text containing no event - *"I cannot make Tuesday, sorry"* - yields one candidate with `title.value` and `temporal.value` both null rather than an empty list. It then survives every check downstream, because a claim whose value is null is perfectly valid, and the user is shown an empty event card for a message that was never an invitation. After the offset fix this is the largest remaining category of wrong results: 1 of 4 negative cases correct.

  **Deliberately not fixed yet.** Two routes, and the choice between them is a judgment call rather than a coding one:

  1. *App-side filter* - drop candidates having neither a title nor a time, in the same transport wrapper as the offset fix. Written and measured during this work, then **backed out** rather than shipped: it treats the symptom, and silently deleting model output needs a higher bar than "it improves a metric". If taken, it must stay narrow - a candidate with a time but no title is a real event the person can name, and dropping it would lose data.
  2. *Prompt fix, upstream* - the wire schema already permits `candidates: []` (a plain array, no minimum), so the model is **choosing** the placeholder rather than being forced into it. The instruction text is `vendor/.../prompt.js`, which is generated by `bun run vendor:scanner`; fixing it means changing the scanner package, which this repo only consumes.

  Route 2 is the correct fix. Route 1 is the one available without leaving this repo.
- [ ] **A failed scan still shows the user nothing.** `ErrorNotification` exists and is not reached on this path. Independent of the cause, a 502 must say so.
- [ ] **Failures are still charged a full reservation.** $0.02 per failure against a $1/day global pot - see task 201. Much less pressing now that failures are rare, but unchanged.
- [ ] `/api/summarize` returned 200 alongside a successful scan after this fix. Task 199 may share this root cause; re-measure before investigating it separately.
